# Aivory Cerveau — Patch Series over upstream zeroclaw

**What this repo is:** Aivory's fork of [zeroclaw-labs/zeroclaw](https://github.com/zeroclaw-labs/zeroclaw)
(Apache-2.0), product name **Aivory Cerveau** — the multi-tenant deployable-agent engine behind
the Aivory user dashboard (Telegram/Slack/WhatsApp/Office Assistant agents).

**Base:** upstream tag `v0.8.4` (rebased from the v0.8.3 series on 2026-08-18; see git log for the rebase-fix commits — the hardest splice was Landlock, where upstream independently rewrote the same child-vs-daemon restriction bug via a different mechanism; Cerveau kept its proven self-re-exec mechanism under upstream's richer ruleset table). Originally bootstrapped on `v0.8.1` for prod parity, moved to `v0.8.2`/`v0.8.3` same day: the durable run/task **control plane only exists from v0.8.2**, and v0.8.3 carries a wave of security hardening — SSRF fixes, constant-time token comparison, RUSTSEC bumps.

**Runtime config vs this repo:** ERP toolkit wiring (Composio-hosted `aivory-erpnext-erp` MCP server, risk tiers, agent-type bundles — docs/CERVEAU-ERP-INTEGRATION-PLAN.md in the AVRY-V2-Main monorepo) is live `config.toml` on the deployment hosts, deliberately not a source patch: it changes tool *policy*, not engine code.
**Branch model:** `cerveau-main` = upstream base + the patch series below, kept **rebase-friendly**:
every Cerveau change is a focused commit on top of upstream, documented here. Where a change is
generic (not Aivory-specific), we attempt to upstream it and drop it from this series.
Upstream is not mirrored in this repo — add it as a remote when rebasing:

```
git remote add upstream https://github.com/zeroclaw-labs/zeroclaw.git
git fetch upstream --tags
```

**Planning docs** (in the private `AVRY-V2-Main` monorepo): `docs/DEPLOYABLE_AGENT_RUNTIME_PLANNING.md`
(phased execution plan) and `docs/ADR-001-AIVORY-CERVEAU-PHASE0.md` (fork scope decisions).

## Patch series

| # | Patch | Why | Touches |
|---|---|---|---|
| 0001 | Replace upstream CI with `cerveau-build` | Upstream's ~25 workflows target their release/publish infra (secrets we don't have; scheduled jobs we don't want). One workflow builds the one artifact we deploy: `zeroclaw` for `x86_64-unknown-linux-gnu`, same recipe as upstream's v0.8.3 release (toolchain 1.96.1, `cargo web build` for the embedded dashboard, feature set resolved via `cargo run -p xtask --bin generate -- features --selection dist`) | `.github/workflows/` |

| 0002 | P-identity: per-request tenant identity resolution | Tenant-scoped `/webhook` turns for dynamically-provisioned identities (no config alias/reload per tenant). `X-Tenant-Id`+`X-Agent-Type` headers (webhook-secret mandatory, fail-closed resolver), persona from `product.agent_profiles` via bounded TTL LRU, rendered as inert fenced operator data appended after host security rules; memory bound to the tenant via `create_memory_for_tenant` (empty allowlist = structurally jailed); install-wide autosave skipped on tenant turns; `principal_id` stamped on delegate/subagent task records. Vanilla paths bit-for-bit unchanged when headers absent | `zeroclaw-memory/src/lib.rs`, `zeroclaw-runtime/src/agent/{tenant.rs,mod.rs,loop_.rs}`, `zeroclaw-runtime/src/tools/{delegate.rs,spawn_subagent.rs}`, `zeroclaw-gateway/src/{tenant.rs,lib.rs,a2a.rs}`, gateway `Cargo.toml` |

| 0003 | P-isolation (slice 1): adversarial cross-tenant tests as a CI gate | Five attack-shaped tests over the exact production mechanism (shared SQL backend + per-tenant `AgentScopedMemory` with empty allowlist): keyword/wildcard/empty recalls, shared-session-id bridging, caller-allowlist widening, exact-key lookup, and host-default-scope visibility — all must return nothing. Wired into `cerveau-build` before the release build: a red isolation test never ships an artifact. (Slice 2 later: same suite against a real Postgres service container) | `zeroclaw-memory/tests/tenant_isolation.rs`, `.github/workflows/cerveau-build.yml` |

| 0004 | F-2 (primitive): durable tool-idempotency ledger | Closes the mid-turn-crash replay window (a replayed turn re-running a side-effectful tool). SQLite ledger in `control_plane.db` with a claim/complete/release protocol: `Claimed` → execute+complete, `AlreadyDone(output)` → reuse never re-execute, `InFlight` → crash case. Length-prefixed SHA-256 key over principal+task+turn+tool+args. 6 tests. Hot-loop wiring + F-1 auto-resume deferred (see ADR-003) | `zeroclaw-runtime/src/control_plane/{tool_idem.rs,mod.rs}` |

| 0005 | Postgres memory lifecycle (tenant-scoped retention + budget) | Upstream lifecycle (hygiene/budget) is SQLite/filesystem-only; the Postgres backend had no bounded-growth path (ADR-004). Adds `PostgresMemory::{init_lifecycle_schema,set_tenant_quota,run_lifecycle}` — one set-based pass enforces age retention (core exempt) + per-tenant budget for ALL tenants at once via `row_number() PARTITION BY agent_id`, with a per-tier `cerveau_tenant_quota` override table LEFT JOINed in. Embedding dims locked at 768 (ADR-004). CI now runs a Postgres service container; 3 integration tests (per-tenant independence, quota override, core-durable retention) | `zeroclaw-memory/src/postgres.rs`, `zeroclaw-memory/tests/pg_lifecycle.rs`, `.github/workflows/cerveau-build.yml` |

| 0006 | Long-term tenant memory: OR-recall + auto-consolidation | Two fixes so "the agent remembers its customer" actually works. (a) **P-recall-scope**: Postgres `recall`/`recall_for_agents` built the keyword filter with `plainto_tsquery` (implicit AND) so a query missing one word skipped an obviously relevant row; now composes an OR `to_tsquery` from the query lexemes, ranked by `ts_rank_cd` (punctuation-only → NULL tsquery, no match, no error). Memory tools already pass `session_id=None`, so recall is tenant-wide across sessions — the earlier "session B forgets" was this AND bug, not scoping. (b) **P-consolidation**: upstream ships `consolidate_turn` with NO call sites; wire it as a background spawn after tenant turns (zero added reply latency, writes through the already-tenant-scoped memory handle; vanilla turns untouched). `model_provider` binding Box→Arc so the spawn can share it | `zeroclaw-memory/src/postgres.rs`, `zeroclaw-memory/tests/pg_lifecycle.rs`, `zeroclaw-runtime/src/agent/loop_.rs` |
| 0007 | Upstream bug fix: schema-scope the v3 memory migration's constraint checks | `migrate_postgres_memory_to_v3` checked `pg_constraint.conname` with no schema scope, so a second schema whose `memories` table reused the same constraint names (`memories_agent_id_notnull_chk`/`_fk`, `memories_agent_key_uniq`) would see the first schema's constraint, skip its own `ADD ... NOT VALID`, then fail at `VALIDATE CONSTRAINT` (ADR-004 §5). Never hit in prod (single `cerveau` schema) but deterministic for any second schema, not just concurrent ones. Fix joins `pg_class`+`pg_namespace` into the existence check. Candidate to upstream | `zeroclaw-config/src/schema/v2.rs`, `zeroclaw-memory/src/postgres.rs`, `zeroclaw-memory/tests/{pg_lifecycle.rs,pg_v3_migration_schema_scope.rs}` |
| 0008 | Upstream bug fix: pgvector-init-thread crash-loop (unblocks vectors) | `PostgresMemory::new` ran `try_enable_pgvector` back on whatever thread called `new()` after the dedicated init thread returned. `try_enable_pgvector` drives the sync `postgres::Client`'s own internal Tokio runtime via `block_on`; when `new()` is invoked from a thread already running inside the daemon's async runtime, entering a second runtime panicked ("Cannot start a runtime from within a runtime"), crash-looping the daemon (ADR-004 §4b item 1). Fix folds `try_enable_pgvector` into the same spawned OS thread already used for schema init/migration, so every blocking Postgres call at construction time stays off the async runtime's threads. Until this landed, `vector_enabled` stayed `false` in prod. Adds a regression test that calls `new(pgvector_enabled=true)` directly from inside a multi-threaded Tokio test body (the exact panicking shape) and asserts it doesn't panic | `zeroclaw-memory/src/postgres.rs`, `zeroclaw-memory/tests/pg_vector_init_thread.rs` |
| 0009 | P-consolidation cost knob | Patch 0006 wired `consolidate_turn` as an unconditional background spawn on every tenant turn (one LLM sub-call each). ADR-004 §4b item 3 flagged this as needing a gate before scale. Adds `[memory] consolidation_enabled` (bool, default `true`) and `consolidation_sample_rate` (0.0-1.0, default `1.0` = unchanged behavior) to `MemoryConfig`; the sampling decision is a pure `should_consolidate(rate, roll)` helper (4 unit tests: rate=1 always in, rate=0 never in, mid-rate boundary, out-of-range clamps) so an operator can turn distillation off or dial it down without touching code | `zeroclaw-config/src/schema.rs`, `zeroclaw-runtime/src/agent/loop_.rs` |
| 0010 | Phase 4.1 (slice 1): tenant-entity-scoped MCP servers (Composio-as-MCP groundwork) | The planning doc's Phase 4.1 requires "Composio entity resolved from the authenticated tenant, never from LLM-influenced content" — but `mcp_servers_for_agent` resolved purely from static per-alias config, with no tenant awareness at all, so a naive `[[mcp.servers]]` entry for Composio could not vary its target account per tenant. Adds `McpServerConfig.tenant_entity_query_param: Option<String>` (e.g. `Some("user_id")`) marking a server as tenant-gated, plus `Config::mcp_servers_for_agent_and_tenant(agent_alias, tenant_platform_user_id)`: with no tenant, a tenant-gated server is dropped entirely (never connects unscoped or to a shared/default account); with a tenant, its `url` gets the entity id appended as the configured query param (existing query strings preserved; an unparseable url fails closed by dropping the server, never connecting unscoped). Also adds `TenantContext::platform_user_id` — the *raw* `X-Tenant-Id`, distinct from the flattened `tenant_id` (which folds in `agent_type`), because Composio connections are per-*user* and shared across a user's agents (ADR-002 D2) so entity scoping must key off the user alone. Wired into `scoped.rs`'s MCP server resolution via `agent::tenant::current_tenant()`. 8 new unit tests (4 config-level: drop-without-tenant, entity-scoped url, existing-query-string append, unparseable-url fail-closed; 1 gateway-level: platform_user_id ≠ tenant_id; plus the pre-existing tenant-context roundtrip test updated for the new field). Does not yet add an actual `composio` server entry to any deployed config, nor the capability graph (4.2) or approval tiering (4.3) — this is the resolution primitive those build on | `zeroclaw-config/src/schema.rs`, `zeroclaw-runtime/src/agent/tenant.rs`, `zeroclaw-runtime/src/tools/scoped.rs`, `zeroclaw-gateway/src/tenant.rs` |
| 0011 | Phase 4.1 follow-on: tenant-agent-type-driven skill bundles | `cerveau-skills/` (4 skills, one per Aivory agent type except `autonomous`) couldn't be installed to a live agent: Cerveau's `[agents.<alias>]` entries are 6 generic host-brain roles, and skills were resolved purely per host alias (`load_skills_for_agent_from_config`), with no notion of the Aivory `agent_type` a tenant turn belongs to. Investigating the *current* (pre-Cerveau) bridge's own multi-agent-type design (`telegram-agent.js`) showed the answer was already proven: `agent_type` is a per-request data value indexing `AGENT_PROMPTS`/`TOOL_REGISTRY` in one running process — never a provisioning axis. Ports that same principle to Cerveau, extending patch 0010's exact pattern rather than inventing a parallel one. Adds `TenantContext::agent_type` (raw `X-Agent-Type`, populated in `build_tenant_context`) and `[agent_type_skill_bundles.<agent_type>]` config (new `TenantSkillBundleConfig{bundles: Vec<String>}`) resolved via `Config::skill_bundle_aliases_for_tenant(tenant_agent_type)` — `None`/unknown type grants nothing (fail closed, same "omission is not a grant" rule as `mcp_servers_for_bundles`). `zeroclaw_runtime::skills::load_skills_for_agent_and_tenant_audited`/`_from_config` grant the host alias's own bundles *and* the tenant's agent-type bundles (first-write-wins/shadow-tracking shared via an extracted `apply_skill_bundle` helper, no duplicated loop). Wired into both `loop_.rs` call sites (`run_tool_call_loop` and `process_message`) via `agent::tenant::current_tenant()`. 4 new tests (3 config-level resolver: none/unknown-type/matching-type; 1 skills-level: host+tenant bundle merge, vanilla turn unaffected, cross-agent-type isolation) | `zeroclaw-config/src/schema.rs`, `zeroclaw-runtime/src/agent/tenant.rs`, `zeroclaw-runtime/src/agent/loop_.rs`, `zeroclaw-runtime/src/skills/mod.rs`, `zeroclaw-gateway/src/tenant.rs` |
| 0039 | Learning-loop tenant guard (Phase 7 of docs/CERVEAU-ERP-INTEGRATION-PLAN.md) | Upstream v0.8.4's `[skills.skill_creation]` / `[skills.skill_improvement]` learning loop writes to and patches the **host** workspace (`config.data_dir`), which every tenant turn's skill resolution also loads (`load_skills_for_agent_and_tenant_audited` starts from the host alias workspace before layering agent-type bundles) — enabling them as-is would let a skill synthesized from one tenant's execution (task + final answer can carry business context) surface in every other tenant's turns, and feed tenant conversation content into the review fork. Guards both post-turn blocks in `run_tool_call_loop` with `current_tenant().is_none()`: learning becomes a host/internal-turn capability only; tenant webhook turns never create, mutate, or pay LLM cost for skills. Per-tenant skill stores are the future fix that would lift this | `zeroclaw-runtime/src/agent/loop_.rs` |

### Planned (per the execution plan; not yet applied)

- **P-isolation (slice 2)** — the isolation suite against a real Postgres service container in CI;
  tenant scoping asserted on `control_plane` task rows once F-1/F-2 land.
- **F-1** — boot-time auto-resume of crashed in-flight tasks. Deferred: needs a goal-execution
  driver seam that does not yet exist (see ADR-003). Own patch after F-2 wiring.
- **F-2 wiring** — thread the landed ledger (0004) into `execute_one_tool`, gated on a deliberate
  side-effect taxonomy (ADR-003). The ledger primitive itself is done.

## Rebase procedure

1. `git fetch upstream --tags`
2. `git rebase <new-upstream-tag> cerveau-main` (patches are focused; conflicts should be small and
   localized — if a patch conflicts hard, check whether upstream implemented the same idea and drop ours)
3. Update this file's table if any patch was dropped/renumbered
4. Push; CI must produce a working artifact before the binary is deployed
